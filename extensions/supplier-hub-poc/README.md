# Supplier Hub 읽기 전용 POC

## 현재 범위 (1단계 + 2단계 + 3단계 + 4단계 + 5단계 + 6단계)

이 확장은 **읽기 전용 골격 검증**만 한다. 아래 외에는 아무 동작도 하지 않는다.

**1단계 (완료, 실제 브라우저에서 검증됨):**

- `supplier.coupang.com` 페이지에서 content script가 실행되는지 확인
- 페이지 제목(`document.title`), URL, hostname, pathname만 읽어서
  console.log와 `chrome.storage.local`에 기록

**2단계 (이번 변경):**

- 현재 화면에 렌더링된 `<table>`들을 훑어서, 헤더 셀 텍스트가
  `구분 / 발주(반출)번호 / SKU번호 / SKU명 / 입고(반출)일자 / 물류센터 / 수량`
  중 몇 개와 일치하는지 점수를 매긴다
- 가장 점수가 높은(4개 이상 매칭된) 표를 "입고상세내역 표"로 간주하고,
  그 표의 헤더 순서를 기준으로 현재 화면에 보이는 데이터 행만 읽는다
- 결과를 console(`[NOIDB-POC] inbound detail rows`)과
  `chrome.storage.local`에 저장하고, 팝업에서 총 행 수 + 첫 3행을 표시한다
- 팝업의 "현재 화면 다시 읽기" 버튼으로 수동 재스캔 가능 (activeTab 권한만 사용)

**중요 — 하드코딩하지 않은 부분:** 특정 CSS class 이름에 의존하지 않는다.
헤더 텍스트 매칭 방식이므로, 실제 마크업의 class 이름은 이번에도 확인하지
않은 상태로 작성했다. 만약 입고상세내역 표가 `<table>`이 아니라 div 기반의
가상 그리드(virtualized grid)라면 이 스캔 로직은 아무것도 찾지 못한다 —
그 경우 콘솔에 `표를 찾지 못함 (최고 매칭 컬럼 수=N, 후보 헤더=[...])`
로그가 남으므로, 이 로그 내용을 공유해주시면 실제 구조에 맞춰 다음 버전을
작성한다 (여전히 추측으로 selector를 넣지 않기 위함).

**3단계 (이번 변경, 미검증):**

- 발주리스트(발주서 목록) 화면에서 `발주번호 / 발주구분 / 진행상태 / 정산상태`
  헤더 텍스트를 기준으로 표를 찾는다 (2단계와 동일한 헤더 매칭 방식,
  class 이름 추측 없음)
- 발주구분에 "매입용"이 포함된 행은 결과에서 제외하고, 제외된 건수를
  `excludedPurchaseTypeCount`로 별도 기록한다 (조용히 버리지 않음)
- 결과를 console(`[NOIDB-POC] order list rows`)과 `chrome.storage.local`에
  저장하고, 팝업 "발주리스트 상태값" 섹션에서 총 행 수/제외 건수/수집 건수와
  전체 행 JSON을 표시한다
- 팝업의 "발주리스트 다시 읽기" 버튼으로 수동 재스캔 가능 (activeTab 권한만 사용)
- **현재 화면(1페이지)에 렌더링된 행만 읽으며, 페이지 자동 넘김은 하지 않는다**
- **3단계는 사용자가 실제 화면에서 검증 완료함.** (이후 실사용 중 발주리스트가
  다단/그룹 헤더 구조임이 확인되어, 아래 "3단계 파서 개선(다단 헤더 대응)"으로
  갱신됨 — 이 개선 자체는 아직 실제 화면 미검증)

**4단계 (이번 변경, 미검증):**

- 발주리스트 화면을 열 때마다(초기 로드 + 재시도 + "발주리스트 다시 읽기")
  이번 스캔 결과를 **발주번호(orderNo)를 키로 하여** 누적 저장소
  (`noidbPocOrderListAccumulated`, `chrome.storage.local`)에 병합한다
- 자동으로 다음 페이지를 넘기지 않는다 — 사용자가 직접 1페이지를 읽은 뒤
  다음 페이지로 이동해 다시 스캔하면, 그 결과가 이전 페이지 결과와
  자동으로 합쳐진다 (수동 순서: 현재 페이지 확인 → 사용자가 다음 페이지로
  이동 → 확장이 다시 스캔 → 누적)
- 같은 발주번호가 다시 읽히면(같은 페이지를 재방문하는 등) 최신 스캔 값으로
  덮어써 **중복 항목이 쌓이지 않는다** — 배열이 아니라 발주번호를 키로 하는
  객체(map)에 upsert하는 방식
- 매입용 행은 병합 이전 단계(3단계 필터)에서 이미 제외되므로 누적 결과에도
  포함되지 않는다. 누적 매입용 제외 건수는 스캔마다 합산해
  `cumulativeExcludedPurchaseTypeCount`로 표시
- 팝업 "발주리스트 누적 결과" 섹션에서 누적 건수, 스캔 횟수, 누적 매입용
  제외 건수, 마지막 스캔 시각과 함께 `발주번호/발주구분/진행상태/정산상태`
  전체 목록을 발주번호순으로 표시
- **4단계(1→2페이지 누적)는 사용자가 실제 화면에서 검증 완료함.**

**진단 기능 (발주리스트 인식 실패 대응, 이번 변경 반영 완료):**

- 발주리스트 표를 찾지 못하면 자동으로, 또는 팝업의 "진단 정보 다시 수집"
  버튼으로 언제든, table/ARIA grid 후보와 발주번호처럼 보이는 숫자 텍스트
  주변의 반복 행 패턴을 수집해 팝업에서 보여준다 — 개발자도구 불필요
- 팝업의 "발주리스트 진단 정보"/"발주리스트 누적 결과" 섹션에 **"전체 복사"
  버튼**을 추가해, 드래그로 선택하지 않고 버튼 한 번으로 클립보드에 복사할
  수 있다 (복사 성공 시 버튼 문구가 잠깐 "복사됨"으로 바뀐다)
- 이 진단을 통해 실제 발주리스트가 `<table>`이며 **다단(그룹) 헤더** 구조임이
  확인됨 — 아래 "3단계 파서 개선"에서 대응

**3단계 파서 개선 (다단 헤더 대응, 이번 변경, 미검증):**

- 기존에는 `<thead>`의 첫 번째 행만 헤더로 읽어, 그룹 라벨(rowspan/colspan)
  아래에 실제 leaf 라벨(발주번호/발주구분/진행상태/정산상태)이 나뉘어 있는
  다단 헤더 구조에서 매칭에 실패했다
- 이제 `<thead>`의 **모든** 헤더 행을 rowspan/colspan까지 반영해 격자로
  펼친 뒤, 각 컬럼 위치의 헤더 텍스트를 위→아래로 이어붙여("정산확인"+
  "정산상태" → 하나의 문자열) leaf 라벨을 문자열 포함(`.includes`) 방식으로
  찾는다 — 특정 구조를 추측해 하드코딩하지 않는다
- **발주구분과 발주유형은 서로 다른 컬럼이다** — 로컬 xlsx의 "리오더" 값은
  "발주유형" 컬럼이고, 화면의 "일반/매입용"은 별도의 "발주구분" 컬럼이다.
  매입용 제외 판정은 반드시 "발주구분" 헤더로 찾은 컬럼만 사용하며, "리오더"
  같은 발주유형 값으로 매입용 여부를 판단하지 않는다
- 발주번호 셀에 "142186781SKU 바코드 출력"처럼 부가 텍스트가 붙어 있어도
  8~10자리 숫자만 정규식으로 추출한다
- 헤더 매칭으로 찾은 발주번호 컬럼이 실제 행 데이터에서 숫자 패턴 적중률이
  낮으면(다단 헤더 오인식 등), 전체 컬럼 중 적중률이 가장 높은 컬럼으로
  안전하게 재판별한다 — 실제 행 구조 기준 판단이며 추측이 아니다
- 정산상태처럼 그룹 헤더 아래 있어 자동 매칭이 여전히 실패할 수 있는 컬럼을
  위해, 실제 thead 원본 구조(행/열 병합 포함)와 각 행의 전체 셀 텍스트를
  결과에 포함시켜, 필요하면 개발자도구 없이 이 정보만으로 다음 라운드에서
  인덱스를 다시 판단할 수 있게 한다
- 빈 정산상태는 빈 문자열 그대로 보존한다(추정하거나 다른 값으로 대체하지
  않음)
- **주의: 이 파서 개선 자체는 아직 실제 화면에서 검증되지 않았다.** 합성
  fixture(다단 헤더를 흉내낸 모의 테이블)로 로직만 검증했다. 아래 검증
  절차대로 실제 화면에서 직접 확인이 필요하다.

**매입용 판정 로직 수정 (실제 화면 확인 후, 이번 변경, 미검증):**

- 실제 화면 확인 결과, "발주구분" 헤더 컬럼의 실제 값은 "리오더" 등
  발주 방식 구분이었다 — "일반/매입용"이 아니었다. **이전 가정("매입용
  제외는 발주구분 컬럼 기준")은 폐기한다.**
- "일반/매입용" 값은 "발주유형" 또는 "주문유형" 컬럼 중 하나에 나타난다.
  어느 쪽인지 추측하지 않고, **이번 페이지의 실제 데이터를 스캔**해 두
  컬럼의 distinct 값과 건수를 모두 집계한 뒤, "매입용" 값이 실제로 나타난
  컬럼만 매입용 판정 기준으로 채택한다 (`detectPurchaseTypeColumn`)
- 두 컬럼 모두에 "매입용" 값이 없으면(이번 페이지 표본에 없을 수 있음)
  판정을 미확정으로 두고, **아무 것도 임의로 제외하지 않는다** — 확인되지
  않은 채 걸러내지 않는다
- 팝업 "발주리스트 상태값" 섹션 위에 "매입용 판정 진단" 블록을 추가해,
  전체 행 수/매입용 제외 수/일반 수집 수/매입용 감지 컬럼(이름+인덱스)/
  발주유형 distinct/주문유형 distinct를 한 번에 보여주며, 여기에도 "전체
  복사" 버튼이 있다 — 개발자도구 불필요
- 정산 판정 컬럼은 "계산서상태"(마지막 정확 일치 컬럼)로 고정 — 발주확정/
  입고진행중/배송완료 등 다른 상태로 정산완료를 추론하지 않으며, 빈값은
  빈값 그대로 둔다
- 진행상태는 "발주상태" 헤더 컬럼 값을 그대로 사용
- **주의: 위 단락은 이후 아래 "매입용 판정 단일 컬럼 고정 + 가상스크롤 수집"
  변경으로 발주유형/주문유형 이중 후보 로직 자체가 제거되었다 — 지금은
  "발주유형" 컬럼 하나만 고정 사용한다. 기록만 남겨둔다.**

**매입용 판정 단일 컬럼 고정 + 가상스크롤(지연 렌더링) 전체 수집 (이번 변경, 미검증):**

- 매입용 제외 판정은 **오직 "발주유형" 헤더 컬럼만** 사용한다. "발주구분"
  (리오더 등)과 "주문유형"은 판정에 전혀 관여하지 않는다(이전 이중 후보
  자동 감지 로직은 제거함 — 사용자가 실제 화면으로 "발주유형" 하나로
  확정함)
- `purchaseType === "매입용"`이면 제외, 그 외(대부분 "일반")는 전부 수집
- **"현재 화면 50행 설정인데 10행만 읽히는" 문제의 원인**: 코드 자체에는
  10행으로 제한하는 로직이 없다(`getDataRows`는 DOM에 실제로 존재하는
  `<tr>`을 전부 반환) — 즉 원인은 파싱 로직 버그가 아니라, **가상
  스크롤(지연 렌더링) UI가 스크롤 뷰포트에 보이는 행만 DOM에 실제로
  생성**하고 나머지는 스크롤해야 생성하기 때문일 가능성이 가장 높다
  (아직 실제 화면으로 100% 확정한 것은 아님 — 아래 검증 절차로 확인 필요)
- 대응: 표를 감싼 "실제로 스크롤되는" 조상(scrollHeight > clientHeight +
  overflow-y: auto/scroll)을 찾아(`findScrollableAncestor`), 있으면 맨
  위부터 끝까지 **읽기 전용으로** 스크롤하며(클릭/입력 없음, 300ms 안팎
  간격으로 재렌더링을 기다림) 매 위치에서 보이는 행을 발주번호 기준으로
  중복 없이 누적한다(`collectAllVisibleRows`). 스크롤이 끝나면(더 이상
  내려가지 않으면) **원래 스크롤 위치로 복귀**한다
- 스크롤 컨테이너를 찾지 못하면(가상스크롤이 아니면) 현재 보이는 행만
  그대로 쓴다 — 이 경우는 화면에 이미 전체 행이 다 있다는 뜻이다
- 화면 추정 전체 행수는 스크롤 컨테이너의 `scrollHeight`를 한 행의 실측
  높이로 나눠 계산한다(측정값, 추측이 아님) — 팝업에 "화면 추정 행수"로
  표시
- 초기 로드+재시도+수동 재스캔이 겹쳐 스크롤 위치가 흔들리지 않도록,
  스크롤 수집이 진행 중이면 새로 시작하지 않고 기존 작업을 재사용한다
  (`scanInFlight` 가드)
- 팝업 "매입용 판정 진단" 블록에 화면 추정 행수 / 실제 수집 고유 행수 /
  매입용 제외 수 / 일반 수집 수 / 매입용 판정 컬럼 / 가상스크롤 감지 여부 /
  발주유형 distinct를 모두 표시하며 "전체 복사" 버튼도 그대로 있다
- **주의: 이 변경 자체는 아직 실제 화면에서 검증되지 않았다.** 50행 중
  10행만 렌더링되는 가상스크롤 상황을 흉내낸 모의 DOM으로 로직만 검증했다
  (일반 49건 수집 / 매입용 1건 제외 / 발주번호 중복 없음 / 스크롤 원위치
  복귀 — 전부 통과). 실제 화면에서 스크롤 컨테이너가 정말로 발견되는지,
  전체 50행이 실제로 다 모이는지 확인이 필요하다.

**아직 하지 않는 것 (의도적으로 보류):**

- 쿠키/토큰/로그인 세션 정보 접근
- 버튼 클릭, 폼 제출 등 어떠한 쓰기/자동화 동작
- 페이지 넘김(pagination) 자동화 — 현재 화면에 보이는 행만 읽음
- Network API 엔드포인트 호출 — DOM만 읽음
- NOID-B 로컬 서버로의 전송 (이 단계는 chrome.storage.local에만 저장)
- "정산완료" 여부를 입고상세내역 존재/날짜로 대체 추정하는 로직 (화면에
  보이는 정산상태 텍스트를 그대로 읽을 뿐, 대체 판단은 하지 않는다)

## Chrome에 로드하는 방법

1. `chrome://extensions` 접속
2. 우측 상단 "개발자 모드" 켜기
3. "압축해제된 확장 프로그램을 로드합니다" 클릭
4. 이 폴더 선택: `extensions/supplier-hub-poc`

   발주번호 키로 정확히 찾아지는지 대조. 매입용 행이 누적 결과에 전혀

### 5단계 검증 절차 — 다단 헤더 파서 (이번 변경, 미검증 — 직접 확인 필요)

1. `chrome://extensions`에서 이 확장을 새로고침(리로드) — 코드가 바뀌었으므로 필요
2. 발주리스트 화면을 새로고침(또는 확장 아이콘 → "발주리스트 다시 읽기")
3. 확장 아이콘 클릭 → 팝업 "발주리스트 상태값" 섹션에서:
   - "발주리스트 표를 아직 찾지 못했습니다" 문구가 더 이상 나오지 않는지
   - 총 행 수(예: 10) / 매입용 제외 건수 / 수집 건수가 표시되는지
4. **성공 조건 확인 (육안 대조, 화면의 실제 1페이지 기준)**:
   - 발주번호가 셀 안에 다른 텍스트(버튼 라벨 등)가 섞여 있어도 숫자만
     정확히 나오는지 (예: "142186781SKU 바코드 출력" → `"142186781"`)
   - 화면 발주구분이 "매입용"인 행이 결과(`rows`)에서 완전히 빠지고,
     "일반"인 행만 남는지 — **"발주유형"(리오더 등) 값과 혼동되지 않았는지
     함께 확인**
   - 진행상태(발주확정/입고진행중/거래처확인요청/거래명세서확인요청 등)가
     화면 그대로 나오는지
   - 정산상태가 화면 우측 계산서 영역과 일치하는지 — **만약 정산상태가
     `null`이거나 비어있는데 화면에는 값이 보인다면**, 팝업 JSON에 함께
     담긴 `theadStructure`(실제 헤더 행/열 병합 구조)와 각 행의 `__rawCells`
     (전체 셀 텍스트)를 "전체 복사" 버튼으로 복사해 공유해주면, 개발자도구
     없이 그 정보만으로 다음 라운드에서 정확한 컬럼 인덱스를 다시 찾는다
   - 빈 정산상태(화면에 값이 없는 행)가 오류 없이 빈 문자열로 나오는지
5. 4단계(누적)도 함께 정상 동작하는지 재확인 (발주번호 upsert, 매입용 누적
   제외 건수 등 — 3~4단계 검증 절차와 동일하게 확인)

**6단계: 발주리스트 자동조회 필터 — 실제 DOM 진단 반영 (이번 변경, 실제 클릭 검증은 아직 필요):**

7단계 진단(아래)으로 사용자가 실제 화면에서 확인해 준 구조를 그대로
반영했다. 더 이상 "발주일"/"최근 30일"이라는 문구를 추측하지 않는다.

- **실제 확인된 구조**:
  1. "기간검색" 라벨 옆에 AntD Select 콤보박스(`input[role="combobox"]`,
     class에 `ant-select` 포함)가 있다. id는 `_r_7_`처럼 렌더링마다 바뀌는
     동적 값이라 **절대 하드코딩하지 않고**, "기간검색" 라벨에서 부모를
     최대 6단계까지 올라가며 그 안에 콤보박스가 **정확히 하나**인 지점을
     찾는다(`resolveDateTypeCombobox`)
  2. 날짜 빠른선택 버튼은 "어제 / 오늘 / 다음 7일 / **다음 30일**"이며,
     "최근 30일"은 존재하지 않는다
  3. 검색 버튼은 `<button type="button">검색</button>`
  4. 같은 화면에 발주서 업로드/발주서 전송 등 업무 버튼이 있다
- **"다음 30일"은 코드 세 군데에서 이중·삼중으로 클릭이 차단된다**: (a)
  애초에 그 텍스트를 찾는 코드 자체가 없음, (b) `trySetPast30DayRange`가
  "오늘"으로 찾은 요소가 "다음 30일"과 같은 요소이거나 같은 텍스트면 즉시
  중단, (c) `selectDateTypeOption`이 찾은 옵션 텍스트가 "다음 30일"과
  같으면 클릭하지 않고 실패 처리
- **"오늘 기준 과거 30일" 만드는 방법** (다음 30일 프리셋이 없으므로
  프리셋 조합만으로는 만들 수 없음): "오늘" 프리셋(업무 변경 버튼이
  아닌, 사용자가 실제 확인한 조회 필터)을 한 번 클릭해 시작일/종료일
  입력값을 "오늘~오늘"로 맞춘 뒤, 그 결과 문자열(예: `2026-09-13`)을
  실제 오늘 연/월/일 값과 대조해 표시 형식을 **역산**하고, 같은 형식으로
  "오늘-29일" 문자열을 만들어 시작일 input에만 다시 써 넣는다(`오늘 포함
  30일` = 오늘부터 29일 전까지). 형식이 애매하면(자리 판별 불가) 아무 것도
  쓰지 않고 포기한다(`shiftDateStringBackDays`)
- **React/AntD 상태에 실제로 반영**: 네이티브 `<input>` value setter로
  값을 바꾼 뒤 `input`/`change`/`keydown(Enter)`/`keyup(Enter)` 이벤트를
  실제로 발생시키고 `blur()`한다(`setReactControlledInputValue`) — 단순히
  `.value`만 바꾸고 끝내지 않는다
- **각 단계가 스스로 검증한다 — 확인 안 되면 검색을 누르지 않는다**:
  1. "기간검색" 라벨 옆 콤보박스를 정확히 하나 찾지 못하면 중단
  2. 콤보박스를 열어 "발주일" 옵션을 정확히 하나(현재 선택값 표시 영역은
     제외하고 새로 열린 드롭다운만) 찾지 못하면 중단
  3. "오늘"/"어제" 프리셋을 못 찾거나, 그 공통 컨테이너 근처(최대 5단계
     확장)에서 편집 가능한 날짜 input을 못 찾거나, "오늘" 클릭 후에도
     두 입력값이 같아지지 않으면 중단
  4. 날짜 형식을 역산하지 못하면 중단
  5. 값을 다시 썼는데 실제로 반영되지 않았으면(React가 되돌림) 중단
  6. 위 어느 단계에서 중단되든 **검색 버튼을 누르지 않고, 플래그도 세우지
     않는다** — 다음 페이지 로드 때 자연스럽게 다시 시도된다
- **"최초 1회"**: `chrome.storage.local`의 영구 플래그
  (`noidbPocAutoFilterApplied`)로 구현. **실제로 검색까지 실행했을 때만**
  플래그를 세우고, 이후로는 이 화면에 다시 들어와도 절대 다시 건드리지
  않는다 — 그래서 사용자가 과거 청산 조회를 위해 직접 기간을 바꿔도
  자동으로 되돌리지 않는다. 팝업의 "1회 재시도 허용" 버튼으로 언제든
  플래그를 수동 초기화할 수 있다
- **무한 재실행 방지**: 이 필터 적용 자체는 페이지 로드당 1.5초 지연 후
  **딱 한 번만** 시도하며, 표 스캔처럼 여러 번 재시도하지 않는다. 실패하면
  (플래그 미설정) 다음 실제 페이지 로드/새로고침 때 다시 한 번 시도되는
  구조라 같은 로드 안에서 반복 클릭이 발생할 수 없다
- **위험 버튼 차단**: 모든 텍스트/요소 탐색은 `!el.closest("table")`로
  표 내부를 완전히 제외하고, "검색/조회/검색하기/조회하기", "기간검색",
  "발주일", "오늘/어제/다음 7일"과 **정확히 일치**하는 요소만 대상으로
  하므로 "발주서 업로드"/"발주서 전송"/"선택한 발주서 전송"/체크박스/
  상태변경 버튼과 텍스트가 겹칠 가능성이 없다

**⚠️ 아직 남은 것 — 실제 브라우저 클릭 검증**: 이번 세션은 브라우저
자동화 도구가 연결되지 않아 위 로직을 실제 클릭으로 끝까지 확인하지
못했다(문법 검사와 논리 점검까지만 완료). 특히 다음 두 가지는 실제
화면에서만 100% 확인 가능하다:
1. 날짜 입력칸이 실제로 "편집 가능한 `<input>`"인지(읽기 전용이라
   타이핑이 막혀 있다면, 위 3번 검증 단계에서 "오늘 클릭 후 값 불일치"로
   안전하게 멈추고 진단만 남긴다 — 검색은 실행되지 않는다)
2. 날짜 입력칸이 정확히 프리셋 버튼들의 부모/조상 트리 안에 있는지(다른
   위치에 있다면 "입력칸을 못 찾음"으로 안전하게 멈춘다)

### 6단계 검증 절차 (실제 화면에서 1회 확인 필요)

1. `chrome://extensions`에서 이 확장을 새로고침(리로드) — 코드가 바뀌었으므로 필요
2. **팝업을 먼저 열어 "자동조회 필터" 상태가 "정보 없음"인지 확인** (이미
   플래그가 서 있다면 "1회 재시도 허용" 클릭 후 진행)
3. 발주리스트 화면을 열거나 새로고침한다 — **이때 화면을 지켜본다**:
   - 화면이 스스로 "기간검색"을 열어 "발주일"을 선택하고, "오늘"을 눌러
     날짜를 맞춘 뒤 시작일을 다시 쓰고, 검색 버튼을 누르는 흐름이 보이는지
   - "다음 30일", 체크박스, 발주전송, 업로드, 상태변경 등은 전혀 건드리지
     않는지
4. 팝업을 열어 "자동조회 필터" 섹션 확인:
   - `dateTypeSelect.ok`, `dateRange.ok`가 모두 `true`이고 `clicked: true`인지
   - `dateRange` 안의 `todayStr`/`targetStr`/`finalStart`/`finalEnd` 값이
     실제로 "오늘"과 "오늘-29일"에 해당하는지 (예: 오늘이 2026-09-13이면
     `finalStart`가 2026-08-15 근처, `finalEnd`가 2026-09-13이어야 함)
5. **성공 조건 확인**: 검색 후 "발주리스트 상태값" 섹션이 새로 조회된
   결과(발주일 기준 최근 약 30일)로 갱신되는지, 화면에 보이는 실제 조회
   기간 표시와 일치하는지 육안 대조
6. 페이지를 **다시 새로고침**해서, 이번엔 자동으로 아무 것도 클릭하지
   않는지 확인 — "1회만" 검증
7. **과거 조회 보호 검증**: 화면에서 직접 기간을 과거로 바꿔 검색한 뒤
   새로고침해도 자동으로 되돌아가지 않는지 확인
8. 만약 3~4번 단계에서 실패했다면: 팝업 "자동조회 필터" 섹션의 진단
   JSON(`dateTypeSelect`/`dateRange`의 `reason` 필드)을 "전체 복사"로
   공유해주면 그 실패 지점만 최소 수정한다

**7단계: 필터바 실제 DOM 진단 (읽기 전용, 유지):**

- 위 6단계 구현의 근거가 된 실제 DOM 확인에 사용한 읽기 전용 진단 기능을
  그대로 유지한다. 발주리스트 화면 진입 시 1.2초 후 자동으로 1회 수집하며,
  팝업의 "발주리스트 필터바 DOM 진단" 섹션에서 "필터바 진단 다시 수집"
  버튼으로 언제든 다시 수집하고 "전체 복사"로 공유할 수 있다
- 6단계 검증 중 문제가 생기면(위 8번), 이 진단도 함께 다시 수집해 공유하면
  원인 파악에 도움이 된다
