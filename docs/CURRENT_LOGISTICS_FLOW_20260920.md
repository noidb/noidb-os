# 물류 업무 기준 — 2026-09-20 사용자 확정

이 문서는 현재 사용자 요청과 이번 확인 결과를 기록한다. 예전 피킹·과거청산 설계를 복원하지 않는다.

## 실제 업무

1. Supplier Hub 신규 발주서리스트를 사용자가 다운로드한다. 원본 위치는 `G:\내 드라이브\쿠팡데이터\발주서리스트다운`이다. NOID-B에서 사용자가 가져오기를 눌러 반영한다.
2. 같은 발주서를 선택해 Supplier Hub의 발주서 업로드 양식을 `G:\내 드라이브\쿠팡데이터\발주서업로드양식`에 다운로드하고, 수정 없이 Supplier Hub에 업로드하면 발주확정이 끝난다. NOID-B의 별도 확정서류 생성이나 `발주서업로드완성`으로의 수동 복사를 필수 조건으로 만들지 않는다.
3. 택배파일 → 쉽먼트 생성 → 쉽먼트 출력세트 → 사용자의 출고완료 처리.
4. 출고한 발주서와 연결된 쉽먼트의 실제 상태를 조회한다. '마감'된 쉽먼트의 SKU별 실제 입고수량을 원발주 수량과 대조한다. 발주서 정산완료나 입고예정일 경과를 쉽먼트 마감으로 대신하지 않는다.
5. 1개 초도입고 SKU는 광고·쿠폰 파일 생성 → 사용자가 Supplier Hub 처리 → NOID-B 처리완료.
6. 미납 SKU는 사용자가 단종 / 거래처발주 / 미납분 재발주요청으로 분류한다. 분류가 저장된 SKU는 미처리 목록에서 빠져야 한다. 다음 목록으로 이동한 것과 최종 외부 업무 완료는 구분한다.
7. 단종은 대기 목록에 누적 → 단종파일 생성 → 사용자가 쿠팡 업로드 → 처리완료 후 대기 목록에서 제외한다.
8. 미납분 재발주도 대기 목록에 누적 → 재발주요청 파일 생성 → 사용자가 쿠팡 업로드 → 처리완료 후 대기 목록에서 제외한다.
9. 거래처발주는 수량·거래처·이미지 등을 검토·수정 → 승인 → 사용자가 카카오톡 전달 → 전송완료로 잠금. 잘못된 행의 수정·삭제 경로와 이력을 보존한다.
10. 거래처 답변 후 결과처리: 단종 / 입고지연 / 거래처수정 / 미납분 재발주요청. 처리된 행은 원래 발주서에서 빠지고 입고지연만 남는다.
11. 거래처수정은 새 거래처의 미전송 초안에 추가한다. 미전송 초안이 없으면 새로 만들고, 기존 전송완료 발주서에 끼워 넣지 않는다. 추가 발주서는 -1, -2 등으로 구분한다.
12. 지연 상품도 나중에 입고되면 재발주요청, 입고불가이면 단종으로 이동한다. 후속 처리까지 끝난 원발주서는 작업 목록에서 빠지고 누적입고와 처리 이력은 남긴다. 재조회해도 재등장하지 않아야 한다.

## 화면·조회 원칙

- 확장프로그램의 신규발주 자동화는 필수가 아니다. 수동 다운로드·업로드가 기본이다.
- 정기 polling, 창 포커스·탭 전환에 따른 재조회, 임의 리디렉션을 없앤다. 최초 표시 이후 사용자가 새로고침할 때만 외부 자료를 다시 가져온다. 저장 시 충돌 검증은 유지한다.
- 피킹 및 물류에 필요 없는 제품DB 수정 단계는 사용자 흐름에서 제거한다. 거래처 표시 등 실제로 필요한 연결까지 무작정 삭제하지 않는다.
- 과거청산 업무를 새로 요구하지 않는다. 사용자가 수동 완료한 건은 원본과 누적입고를 지우지 않고 작업 대상에서 제외한다.
- 바코드 출력은 사용자가 현재 사용하는 모델명 없는 양식·중국 원산지 기준을 유지한다.

## 2026-09-20 직접 확인한 사실

- 운영 `/wms/work-center`에는 '통합 피킹 시작'이 노출된다. 로컬 `app/wms/work-center/page.tsx`와 새 `logistics`, `invoice-group` 경로는 작업 시작 시 이미 미커밋 상태였다. 운영과 로컬이 일치한다고 가정하지 않는다.
- 로컬 첫 화면의 '출고완료'는 `nextInvoiceGroupStage`를 호출하여 실제로 단계를 한 칸씩 올리고 있다. 실제 출고완료 동작과 분리해야 한다. 아직 수정하지 않았다.
- 실제 미납 API는 `calculateSupplierHubShortages`의 발주서 '정산완료'+입고이벤트 경로와 입고상세내역 대체 경로가 남아 있다. 쉽먼트 마감 기반으로 전환되지 않았다.
- Supplier Hub `/ibs/asn/active` 목록의 실제 화면에서 쉽먼트번호·상태·발주번호·입고예정일을 확인했다.
- 마감 쉽먼트 `50570817` 상세의 `shipmentDetailTable`에 발주번호 `142186780`, SKU `38249239` 납품/입고 4/4, SKU `38256621` 3/3이 있고 총 입고 7과 일치한다. 박스 셀에 rowspan이 있으므로 단순 셀 인덱스만으로 읽으면 안 된다.
- 목록 페이지 2의 실제 읽기 요청은 GET `/ibs/shipment/parcel/list?pageNumber=2&centerCode=&carrierCode=&estimatedDeliveryDate=&shipmentSeq=&purchaseOrderSeq=`이며 HTML을 반환한다. 전체 86페이지가 관찰됐다. 발주번호 필터는 실제 UI로 검증한 뒤 사용해야 한다.
- 상세 조회 주소는 `/ibs/shipment/parcel/{shipmentNumber}`다. 마감 날짜는 확인한 목록·상세 화면에 없다. 도착일이나 입고예정일을 마감일로 간주하면 안 된다.

## 아직 남은 연결

- 출고한 PO만 대상으로 사용자가 실행하는 쉽먼트 읽기 수집을 구현·검증한다. 연결된 모든 쉽먼트의 조회 범위가 완전한지 확인하고 일부가 미마감이면 최종 미납 계산을 보류한다. 저장은 쉽먼트/박스/PO/SKU 식별자를 보존하고 재수집해도 수량을 이중 가산하지 않는다.
- 원발주 확정수량과 최종 입고수량을 대조한다. 납품수량-입고수량만 사용하면 처음부터 보내지 않은 수량이 빠진다.
- 초도 1개입고 광고·쿠폰, 미납 분류, 각 후속 큐의 최종 완료를 위 출고 발주서와 연결해야 한다. 현재 전체 흐름 완료로 보고하면 안 된다.
- 사용자에게 확인 요청 중: '9월 17일꺼까지'가 입고예정일 기준인지, 실제 마감일 기준인지. 확인 없이 날짜로 운영 데이터를 일괄 제외하지 않는다.
- 기존 미커밋 물류 변경을 보존하고, 실제 운영 반영은 별도 승인 후 수행한다.
