# 구글시트 구조 비교 및 추천안

`lib/wms/types.ts`에 정의한 창고 위치 데이터 모델을 실제 구글시트로 어떻게 담을지에 대한
비교와 최종 추천이다. **아직 실제 시트를 만들지 않았다.** 기존 시트(`제품DB`, `발주서 출력`
등)의 열/수식/데이터는 이 문서의 어떤 안을 채택하든 전혀 건드리지 않는다.

## 비교 대상 3안

- **A. 제품DB에 위치 열 추가** — 기존 `제품DB` 시트에 Zone/Shelf/BOX 등 열을 그대로 추가
- **B. 창고위치 마스터 단일 시트** — 새 시트 1개에 모델 위치 + SKU 예외 위치를 함께 저장
- **C. 3개 시트 분리** — `BOX 마스터` + `모델 위치` + `SKU 예외 위치`를 각각 별도 시트로 분리
  (`lib/wms/types.ts`의 WarehouseBox / ModelLocation / SkuLocation과 1:1 대응)

## 비교표

| 기준 | A. 제품DB 열 추가 | B. 창고위치 단일 시트 | C. 3개 시트 분리 |
|---|---|---|---|
| **6000 SKU 규모** | SKU 행마다 값 채워야 함 — 입력량 가장 많음 | 모델+예외만 저장하면 되어 입력량 적음, 단 한 시트에 레벨(모델/SKU) 구분 열 필요 | 입력량 가장 적음 (BOX는 수십~수백 행, 모델 위치는 모델 수만큼, 예외는 극소수) |
| **다중 옵션(같은 모델 여러 옵션)** | 옵션마다 반복 입력 필요 — 상속 이점을 못 살림, 입력 실수로 옵션 간 값 불일치 위험 | 상속은 가능하나 "이 행이 모델 레벨/SKU 레벨"을 구분하는 부가 로직 필요 | 상속 구조를 시트 레벨에서 그대로 구현 — 설계 의도와 가장 정확히 일치 |
| **피킹 속도** | 조인 단계 1개 적어 이론상 최상 | 발주서 출력 + 제품DB + 창고위치(1개) = 3개 시트 조인 | 조인 단계가 1개 더 많음(최대 4~5개 시트). 단, 시트 API는 시트마다 1회씩 통째로 읽어오는 방식이라 SKU 수(6000개)에 비례해 느려지지 않으며, 시트 개수가 늘어도 API 호출 횟수만 소폭 늘 뿐 체감 속도 차이는 크지 않음 |
| **유지보수** | **기존 시트 구조를 직접 변경 — 이번 스프린트 규칙("기존 시트 열 변경 금지")과 정면 충돌.** 기존 Apps Script(`PRODUCT_DB_HEADERS` 등)가 열 순서/개수를 엄격히 관리하므로 실수로 기존 로직을 깨뜨릴 위험이 매우 큼 | 기존 시트는 안 건드려 안전하지만, 박스 자체 메타데이터(용량/QR/사용상태)를 넣을 공간이 마땅치 않아 결국 시트가 갈릴 가능성이 높음 | 관심사가 명확히 분리되어(박스 정보 / 모델-박스 매핑 / SKU 예외) 유지보수성이 가장 높음. QR·용량·사용상태를 위한 전용 공간이 처음부터 있음 |
| **확장성** | 창고 재편성 시 6000행을 개별 수정해야 함 — 낮음 | 중간 — 이후 QR/용량 관리가 필요해지면 결국 분리해야 함 | 가장 높음 — 이번에 설계한 타입 구조와 정확히 대응되어, 이후 실제 DB로 옮기더라도 스키마 변경이 거의 없음 |
| **이번 스프린트 규칙 준수 여부** | ❌ 위배 (기존 시트 열 변경 금지 규칙과 충돌) | ✅ 가능 | ✅ 가능 |

## 최종 추천: **C안 (BOX 마스터 + 모델 위치 + SKU 예외 위치, 3개 시트 분리)**

이유:
1. 기존 시트를 전혀 건드리지 않아 "기존 상품등록 기능 절대 수정 금지" 원칙을 완전히 지킨다 (A안은 이 원칙과 충돌해 사실상 선택 불가).
2. 모델 상속 + SKU 예외라는 설계 의도를 시트 구조 레벨에서 가장 정확하게 구현할 수 있다.
3. BOX 자체의 메타데이터(QR 값, 용량, 사용상태, 메모)를 위한 전용 공간이 처음부터 있어, QR 설계·모바일 관리 요구사항과 자연스럽게 맞물린다.
4. 6000 SKU 규모에서 실제 사람이 입력해야 하는 행 수가 가장 적다 — 운영 부담이 가장 낮다.
5. 유일한 단점(조인 단계가 하나 더 늘어남)은 구글시트 API 특성(시트 단위 전체 조회) 때문에 실질적인 속도 저하로 이어지지 않는다.

## C안 시트 상세 설계

### 시트 1: `BOX마스터`

| 컬럼 | 설명 |
|---|---|
| BOX ID | 고유키. 예: `E-A-001` |
| BOX 종류 | `소형공구박스` \| `큰리빙박스` |
| Shelf ID | 예: `E-A` |
| Zone | 예: `E` |
| 카테고리 | 예: `귀걸이` |
| 시리즈 | 예: `나비` (선택) |
| 세트상품여부 | `Y` / `N` |
| 최대모델수 | 숫자 (선택, 용량 제한 있을 때만) |
| QR값 | QR 코드에 인코딩할 값 (docs/WAREHOUSE_QR_PLAN.md 참고) |
| 사용상태 | `사용중` \| `비어있음` \| `가득참` \| `폐기` |
| 메모 | 자유 텍스트 |
| 정렬순서 | 숫자 |

**"현재모델수"는 이 시트에 저장하지 않는다** — 화면에서 `모델위치` 시트를 boxId 기준으로 세어서
그때그때 계산해 보여주는 것을 권장한다(스프레드시트 수기 관리 환경에서 캐시 필드는
어긋나기 쉽다).

### 시트 2: `모델위치`

| 컬럼 | 설명 |
|---|---|
| 모델명/품번 | 고유키. 제품DB의 "모델명/품번"과 동일 텍스트 |
| 기본BOX | BOX ID |
| 보조BOX | BOX ID (선택) |
| 옵션전체같은BOX | `Y` / `N` |
| 위치메모 | 자유 텍스트 |
| 최근수정일시 | |
| 수정자 | (선택) |

### 시트 3: `SKU예외위치`

| 컬럼 | 설명 |
|---|---|
| SKU ID | 고유키. 제품DB의 "SKU ID"와 동일 |
| 모델명/품번 | 조회 편의용 |
| BOX ID | 이 SKU만 예외로 위치한 BOX |
| 옵션명 | 조회 편의용 (예: "실버") |
| 최근수정일시 | |
| 수정자 | (선택) |

이 시트는 **정말 예외인 SKU만** 들어간다. 대부분의 SKU(옵션 전체가 같은 BOX인 경우)는
이 시트에 아무 행도 없어야 정상이다.

## 조회 시 조인 순서 (읽기 전용)

```
발주서 출력 (SKU, 발주수량, 입고예정일, 물류센터...)
      +
제품DB (SKU, 상품명, 이미지, 거래처, 모델명/품번...)
      +
모델위치 (모델명/품번 → 기본/보조 BOX)
      +
SKU예외위치 (SKU → 예외 BOX, 있으면 모델위치보다 우선)
      +
BOX마스터 (BOX ID → Zone/Shelf/시리즈/세트여부/사용상태...)
      ↓
"Zone → Shelf → BOX → 모델 → SKU" 피킹 뷰
```

Sprint 1에서 만든 `lib/wms/google-sheets.ts`(읽기 전용 Sheets API 클라이언트)를 그대로
재사용하면 된다. 새 시트 3개를 각각 `fetchSheetRows()`로 읽어 SKU ID / 모델명 / BOX ID
기준으로 자바스크립트에서 조인하는 방식으로, 이미 `lib/wms/purchase-orders.ts`가 쓰고 있는
패턴을 그대로 확장하면 된다 (이번 스프린트에서는 구현하지 않음, 설계만).
