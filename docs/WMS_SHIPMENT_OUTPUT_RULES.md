# WMS 쉽먼트 출력세트 고정 규칙

실사용 테스트에서 확정한 규칙이다. 명시적인 사용자 변경 요청 없이 변경하지 않는다.

## 데이터 원본

- SKU ID, 상품바코드, 상품명, 옵션명, 발주수량은 `발주서리스트다운` 발주서 원본을 유일한 기준으로 사용한다.
- 최종 납품수량은 해당 발주 원본으로 생성된 **현재 선택 Shipment 업로드 XLSX의 J열**과 동봉내역서가 정확히 일치해야 한다. 확정 과정에서 줄인 정상 납품수량을 원발주 수량으로 되돌리지 않는다. 원발주 수량을 초과한 경우는 차단한다.
- 웨이브 저장값이나 제품DB 상품명으로 위 발주서 값을 덮어쓰지 않는다.
- 제조국과 모델명만 SKU ID를 기준으로 제품DB에서 보강한다.
- 현재 선택한 출고작업 묶음(generation)의 발주번호 집합과 쉽먼트 XLSX의 대상 발주번호 집합이 정확히 일치할 때만 생성한다. 부분 성공은 금지한다.

## 상품명과 옵션명

- 화면과 출력 XLSX 모두 공용 함수 `resolveDisplayNameAndOption`을 사용한다.
- 상품명에서 `노이드비`, `NOID-B`, `NOIDB`를 제거한다.
- 첫 번째 쉼표 앞은 상품명, 그 뒤의 원문 전체는 옵션명이다.
- 두 번째 옵션과 호수·사이즈를 자르지 않는다.
- 쉼표가 없고 저장 옵션 뒤에 명확한 호수·사이즈가 있으면 실제 상품명 원문의 값까지 옵션에 포함한다.

## 출력 파일과 순서

- 출력세트는 `01_부착문서_4분할.pdf`, `02_동봉내역서_통합.pdf`, `03_바코드출력_YYYYMMDD_최종.xlsx`, `04_물류센터_라벨.xlsx`, `05_거래명세서.pdf`, `06_생성파일목록.txt`로 구성한다.
- 바코드 출력파일은 PDF가 아니라 BarTender용 XLSX다.
- XLSX에는 각 쉽먼트의 `쉽먼트구분` 행과 상품행을 포함한다.
- 상품 순서는 각 `shipment_ManiFest_document`의 동봉내역서 순서를 따른다.
- `번호`는 창고번호·상품분류가 아닌 숫자 순번이다. 각 쉽먼트에서 1부터 시작하고 실제 출력 라벨 한 장마다 1씩 증가한다. 구분행의 번호는 빈칸으로 둔다.
- 라벨 프린터의 물리적 적재 순서에 맞게 구분행을 포함한 전체 데이터 행을 역순으로 기록한다. 마지막 데이터 행이 첫 쉽먼트 구분행이며, 적재된 라벨을 위에서 보면 구분표 → 동봉내역서 상품 순서가 된다.
- `출력유형` 값은 상품행 `상품`, 구분행 `쉽먼트구분`으로 유지한다.
- 재출력센터는 선택 목록 순서대로 1부터 숫자를 배정한 뒤 전체 역순 저장한다. 한 SKU를 여러 장 뽑을 때에도 3장이라면 저장 번호는 `3, 2, 1`이다. 재출력센터 파일에는 쉽먼트 구분행을 추가하지 않는다.
- Shipment 화면의 `바코드 파일만 생성`도 전체 출력세트와 같은 원본 탐색·PDF 대조·동봉내역서 순서를 사용한다. 발주서 행순서만으로 대신 생성하지 않는다.
- 단독 바코드 생성의 서버는 발주번호·SKU·바코드·센터·입고예정일을 현재 발주 원본과, 수량을 실제 선택한 Shipment XLSX의 최종 납품수량과 다시 대조한다. 파일 이름과 발주 집합이 정확히 일치하는 XLSX만 읽으며 동명 파일이 여러 개면 차단한다. 한 상품이라도 누락·중복·혼입되거나 값이 다르면 파일 생성과 Drive 저장을 모두 차단한다.

## BarTender 연결 형식과 검증 범위

- 시트 이름은 `템플릿1`을 유지한다. Excel 연결의 시트 목록에서는 `템플릿1$`로 보일 수 있다.
- 열 이름과 순서는 `SKU ID`, `번호`, `바코드`, `상품명`, `옵션명`, `제조국명`, `모델명`, `출력유형`으로 고정한다.
- 헤더는 A1:H1이고 상품·구분행을 포함하는 구조화 테이블 `BarTenderData`를 보존한다. 기존 BarTender 양식의 연결 필드를 변경하지 않는다.
- 자동 검사는 XLSX 재읽기, 테이블, 전체 행·순번·옵션·출력순서를 검사한다. 이것만으로 설치된 BarTender 프로그램의 연결이나 실제 인쇄까지 확인했다고 보고하지 않는다.
- Windows ACE의 시트 열거·행 조회 성공은 해당 Excel 드라이버의 읽기 검증이다. BarTender에서의 파일 선택·필드 연결·인쇄 성공과는 검증 범위가 다르다.
- 구조화 테이블이 없던 파일도 ACE가 열거할 수 있다. 따라서 과거 연결 오류의 원인을 단순히 “테이블이 없었기 때문”으로 확정하지 않는다. 현재 사용자가 연결 문제 해결을 확인한 파일 구조를 유지한다.

## 변경 방지

- `npm run verify:wms-rules`와 `npm run verify:shipment-manifest-order`가 숫자 순번·전체 역순·동봉내역서 순서·단독/전체 출력 일치와 핵심 규칙을 검사한다.
- `npm run build`는 고정 규칙 검사를 먼저 실행하며, 실패하면 빌드를 중단한다.
- 규칙을 변경할 때는 사용자 확인 후 이 문서와 회귀검사를 함께 수정한다.
