## 1. 오늘 바뀐 흐름

1. **과거청산 삭제** — 메인 '입고결과 확인'(`/wms/vendor-orders`) 화면은 이제 쉽먼트 입고결과 화면. 예전 Aside 처리기록(마감 25건, 쿠폰완료 801 SKU 등)은 비움. 첫 수집 저장 때 이전 입고결과 처리기록(runs·분류·후속처리)도 한 번 비움(`lib/wms/logistics-receipt-reset.ts`).
2. **9/13 이후 마감 쉽먼트 가져오기** — 쿠팡 쉽먼트 화면의 확장 버튼 '입고결과 일괄 가져오기'가 쿠팡 목록 전체에서 **입고예정일 2026-09-13 이후 + 마감** 쉽먼트를 모두 가져온다(`LOGISTICS_RECEIPT_SINCE`). 다시 눌러도 중복되지 않고, 예전 마감건은 목록에서 빠져도 유지.
   - 쿠팡 공급상태 조회가 대부분 비어 와서(조회안됨) **제품DB 발주가능상태로 채움**(화면 새로고침 때 한 번).
3. **입고결과 탭**
   - 미납 SKU 리스트: 쉽먼트 정보 한 칸, 사진·제품링크, 과재고·단종·누적입고 100+ 표시, 미납 빨간색.
   - 버튼: 단종 / 거래처발주 / 미납분 재발주요청. 이미 거래처에 **보낸** 발주(입고대기·지연)가 있는 SKU는 '거래처 발주중' 표시 + **기존 발주로 처리**(기본)·**추가 발주**.
   - 공급상태가 정상이 아닌 줄: **단종확인 / 단종해제** 버튼.
   - 마케팅 SKU 리스트: 전체선택/해제, 쿠폰 **기본 20%, 과재고·누적입고 100+는 30%**(파일 2개로 분리). 무조건 제외 목록 `lib/wms/marketing-permanent-exclusions.ts`(같은 모델 전체 제외, 현재 36839194).
   - **단종 대상 SKU**: 제품DB·보관 탭 현재상태 판매중지·단종·거래처단종·가품중단 + 발주가능상태 정상, 재등록완료 옛 SKU가 아직 정상인 것, 메모(39127489·38248703·36789607). → 단종신청 엑셀·공문 PDF 생성.
   - **단종해제 대상 SKU**: 현재상태 과재고·발주가능상태 정상전환대상·제품DB로 이동(재고있음) + 발주가능상태 정상 아님, 메모 13개(`MEMO_RELEASE_SKU_IDS`), 화면에서 단종해제 누른 것. 재등록SKU 탭·_SKU교체이력·재등록구분(판매량저조/영구/재등록완료)은 제외, 이미 정상인 것도 제외. → 드래그 복사 또는 엑셀 파일.
   - **창고재확인·보관 정리**: 미리보기 후 실행. 창고 확인결과 공란=유지, 거래처단종→보관, 제품DB로 이동(재고있음)→제품DB(현재상태 비움), 보관 탭의 제품DB로 이동(재고있음)도 제품DB로. 실행 전 탭 백업.
4. **재발주요청 화면**(`/wms/inbound/reorder`): 버튼 정리, 아래 **전체 미납 목록**(지금 상태 표시) — 미분류는 추가, 잘못 보낸 단종(신청 전)·거래처발주·기존 발주 처리는 **재발주요청으로 바꾸기**.
5. **거래처 발주서**: 미납 SKU에서 보낸 줄은 제품DB 거래처·모델SKU·바코드·사진으로 채움, 내부 메모는 카드 이미지에 안 나옴, 발주서 작성 화면에도 SKU·바코드 표시(이미지에는 없음). 입고결과에서 직접 거래처발주를 누르면 예전 삭제로 생긴 '제외' 표시를 풀고 넣음.

## 2. 오늘 겪은 문제와 결론

- **저장 실패(ETag mismatch)**: 오후에 저장소 읽기 방식을 바꿨다가 저장이 계속 거절됨 → **원래 방식(useCache:false)으로 되돌림**(`lib/wms/weekly-work-blob.ts`, 발주 저장소). 남긴 보완: 저장 충돌 시 기다렸다 재시도(최대 6번), 반쯤 저장된 거래처발주 예약 자동 정리(`reconcileIncompleteVendorRoutes`), 거래처발주 실패 이유 안내.
- **확장 전송 끊김**: 저장 API가 바로 응답하도록 바꿔 해결(확장 수정 없이).
