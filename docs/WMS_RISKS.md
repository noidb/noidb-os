# NOID WMS 리스크 및 주의사항

## 1. 기존 기능 보호

- `app/page.tsx`, `app/api/*`(기존 상품등록 관련 라우트), `lib/excel/*`, `lib/product-db/*`는
  WMS 작업 중 절대 수정하지 않는다.
- `noidb-os-v1/` 하위 프로젝트는 별개 프로젝트로 간주하고 건드리지 않는다.
- WMS 관련 코드는 `app/wms/*`, `lib/wms/*` 등 새 경로에만 추가한다.

## 2. 데이터 정합성 리스크

- **발주서 불변값 위반**: 같은 `purchaseOrderNumber`에서 SKU/수량이 바뀌는 경로가 생기면
  기존 입고/피킹 이력과의 정합성이 깨진다. API/로직 구현 시 이 값들은 항상 읽기 전용으로 취급해야 한다.
- **원본값 유실**: 입고예정일·물류센터를 변경할 때 `original*` 필드를 덮어써버리면
  변경 이력 추적이 불가능해진다. 항상 `original*`은 최초 생성 시점 값 그대로 유지하고,
  `current*`만 갱신한다.
- **위치 계층 불일치**: 선반/박스/모델/SKU 중 상위 계층이 누락된 상태로 위치 데이터가 저장되면
  피킹 정렬(같은 박스를 한 번만 열기)이 깨질 수 있다.

## 3. 외부 시스템 연동 리스크

- **서플라이어 허브 연동**: 입고예정일/물류센터 변경, 거래처발주 발송은 외부 시스템에 실제 영향을
  주는 작업이다. 반드시 "사용자 승인" 단계를 거친 뒤에만 외부 요청을 보내도록 구현해야 하며,
  Sprint 0 시점에는 이 연동 자체를 구현하지 않는다(타입/문서 수준에서만 설계).
- **승인/거부 결과 자동 감지**: 폴링 주기, 실패 시 재시도, 타임아웃 처리 방식을 다음 스프린트에서
  구체적으로 설계해야 한다. 잘못 설계하면 중복 요청이나 상태 불일치가 발생할 수 있다.
- **구글시트 연동**: 구글시트는 기존 상품등록 기능의 저장소이기도 하므로, WMS가 시트를 사용할 경우
  기존 시트/시트 구조를 공유하지 않고 별도 시트 또는 별도 탭을 사용하는 것을 원칙으로 검토한다.

## 4. 브라우저 자동화 리스크 (신규 발주 감지, 후순위)

- 대상 사이트의 이용약관/로봇 정책을 사전에 확인해야 한다.
- 자동화가 실패하거나 사이트 구조가 바뀔 경우를 대비한 예외 처리와 알림 체계가 필요하다.
- 과도한 요청 빈도로 대상 사이트에 부담을 주지 않도록 폴링 주기를 신중히 설계한다.
- 이 항목은 Sprint 0~4에서는 구현하지 않고, 별도 스프린트에서 리스크를 재평가한 뒤 진행한다.

## 5. 보안/비밀정보 취급

- 환경변수 값, API 키, 인증 토큰 등은 코드/문서/로그 어디에도 평문으로 노출하지 않는다.
- 서플라이어 허브, 구글시트 등 외부 연동에 필요한 인증정보는 `.env` 등 기존 환경변수 관리 방식을
  따르고, 이 문서나 커밋 메시지에 값 자체를 기록하지 않는다.

## 6. 작업 프로세스 리스크

- 모든 WMS 작업은 `feature/noid-wms-foundation`(또는 후속 feature 브랜치)에서 진행하고,
  `main` 브랜치에는 리뷰 후 병합한다.
- 큰 변경 전에는 `before-noid-wms`와 같은 태그/커밋 형태의 안전지점을 남긴다.
- 기존 기능에 영향이 없는지 확인하기 위해, 변경 후에는 항상 `npm run build`로 빌드 성공 여부를
  재확인한다.
