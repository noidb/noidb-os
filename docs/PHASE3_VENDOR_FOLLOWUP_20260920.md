# 거래처 답변 후속 처리 — 로컬 검증 기록

## 이번 범위

사용자의 다음 단계 진행 요청에 따라 기존 거래처 편집기를 유지하고, 거래처 답변을 단종·지연·거래처 변경·쿠팡 재발주로 처리하는 연결을 보완했다. 기존 미커밋 변경을 보존했다. 이번 작업의 커밋·push·배포·운영 데이터 변경·카카오 전송은 하지 않았다.

## 수정

- 거래처 전송 후 진입 버튼을 `결과처리`로 표시하고, 입고결과 화면의 후속처리 탭으로 연결했다.
- 쉽먼트 출처가 있는 초안에는 창성의 실제 미납수량, 다른 거래처의 12개 단위 권장 수량을 표시한다. `권장 수량 적용`을 눌렀을 때만 주문수량이 바뀐다. 수동 입력과 원본 미납수량은 구분한다.
- 거래처 변경 시 원본 쉽먼트·발주번호별 미납 증빙을 보존한다. 대상의 미전송 초안을 재사용하며 승인 상태였다면 재검토 상태로 전환한다. 전송완료 발주서만 있으면 새 초안을 만들고 기존 발주 이력은 유지한다. 같은 SKU의 서로 다른 쉽먼트는 합산하며 겹치는 출처는 차단한다.
- 거래처 답변에서 재발주로 이동할 때 옛 입고상세 자료 대신 마감 쉽먼트의 출처별 수량을 사용한다. 여러 출처는 출력 파일에서만 발주번호·SKU별 합산하고, 완료 기록은 쉽먼트 출처별로 남긴다.
- 파일 생성 후 들어온 다른 쉽먼트는 이전 파일 완료에 포함되지 않는다. 최종 단종·재발주 완료 시 연결된 원본 거래처 후속 업무도 활성 목록에서 제외하고 기록을 유지한다.
- 기존 입고상세 기반 자료의 서로 다른 발주번호 합산 누락도 보정했다. 사용자가 바꾼 발주수량과 쉽먼트 기반 분기를 유지했다.
- 거래처 카드 출력은 최신 완료 검사에서 반환한 상품만 출력하고, 이력 조회에서는 전송완료 저장을 막는다.

## 검증 결과

모든 데이터 저장과 외부 응답은 메모리 대체로 검증했다. 실제 쿠팡·Google Sheets·Drive 자료를 바꾸거나 카카오톡을 보내지 않았다.

- `verify-vendor-shipment-reorder-flow.ts`: 실제 입고 보드와 분류 예약, 거래처 이동 함수, 저장 reducer, 실제 재발주 XLSX 생성, 파일 증빙 완료 연결 통과. 거래처 주문 12와 미납 2+3=5 분리, 나중 들어온 4 유지, 출처별 완료 이력 합계 5, 원본 후속 업무 종료, 단일 출처 배열 완료, 재시도 중복 방지 확인.
- `verify-logistics-vendor-browser.cjs`: 로컬3111의 실제 공용 거래처 편집기에서 수량18 수정→승인→전송완료→다시 열기→결과처리→입고지연 메모 저장→다시 열기 통과. 실제 저장 reducer를 사용하되 API는 모두 가로채고, 외부 주소와 모르는 API는 차단했다. 테스트용 사이트 모드는 추가하지 않았다.
- `verify-logistics-vendor-transfer.cjs`: 대상 초안 재사용, 새 발주 구분, 승인 해제, 같은 SKU 다른 쉽먼트 합산, 출처 중복 차단, 원본 보존과 재시도 통과.
- `verify-logistics-follow-up-api.cjs`: 단종 파일 증빙, 정확한 요청 ID 완료, 뒤늦게 추가된 요청 보존, 연결된 원본 거래처 업무만 종료, 잘못된 완료 입력의 외부 저장 차단 통과.
- 기존 직접 재발주 XLSX/완료, 쉽먼트 분류, 출처 검증, 거래처 큐 및 legacy 입고 전체 연결 검증 통과. 이전 `verify-clearance-lifecycle.cjs`의 2+3 합산 실패가 해소되었다.
- 수정 대상 TypeScript 진단 0건, 범위 한정 공백 검사 통과. 전체 빌드·전체 테스트는 실행하지 않았다.

## 거래처 화면 정돈

- 결과처리 버튼을 같은 크기의 3열 2행으로 배치했다. 첫째 줄은 미납분재발주요청·단종으로 이동·거래처 수정, 둘째 줄은 보충분 입고완료·입고지연·삭제다.
- 웨이브 목록·간단입고·예전 입고 메뉴와 중복 제목·긴 설명·미등록 안내를 제거했다. 일괄 선택은 접어두고 결과처리 중에는 출력 패널을 숨겼다.
- PC와 모바일의 버튼 개수·배치·크기, 기존 수량·승인·전송·지연 저장, 이동한 삭제 버튼의 실제 reducer 처리를 격리된 브라우저 테스트로 확인했다. 수정 TSX 7개 타입 진단은 0건이다.
- 로컬 화면만 수정했으며 운영 데이터 변경과 배포는 하지 않았다.

## 승인 단계 제거와 전송 카드 통일

- 별도 승인 없이 초안에서 수정·이미지 저장·전송완료를 진행한다. 기존 승인완료 자료도 미전송이면 편집할 수 있고 기존 상태 이력은 보존한다.
- 화면 카드와 PNG 다운로드는 같은 생성 결과를 사용한다. 발주일을 고정하고 사진과 이미지 결과를 재사용하며, 숨긴 전송완료 발주서의 카드는 생성하지 않는다.
- 이미지 저장 전 수정 내용을 저장한다. 저장 실패 시 다운로드와 전송완료를 진행하지 않는다. 이미지 준비 중 내용이 달라지면 다시 저장하도록 안내한다.
- 전송완료 발주서는 발주결과처리 버튼으로만 열며, 닫힌 발주서는 전체선택 삭제에서도 제외한다.
- 격리 브라우저에서 사진 포함 카드와 PNG 바이트 일치, 저장 실패, 최신 수량 직접 전송, 기존 승인 자료 편집, 잠금, 결과처리 지연·삭제, PC/모바일 6개 버튼 배치를 검증했다. 카카오톡 실제 전송이나 운영 데이터 쓰기는 하지 않았다.

## 카드 표시 순서와 배송주소

- 사용자 지정 용어를 `주문수량`으로 통일했다. 카드 순서는 큰 상품 사진 → 상품명 → 옵션명 → 주문수량이며 SKU 번호와 바코드는 표시하지 않는다. 내부 상품 식별값은 유지한다.
- 배송주소는 기존 값을 유지한다. 최종 사용자 지시에 따라 연베이지 배경에 테두리 없이 표시하고, `배송지 정보` 제목은 그린 버튼 모양으로 분리했다. 초안과 다운로드는 같은 카드 이미지를 사용한다.
- 제목은 72px, 실제 주소·받는 사람·전화번호는 동일한 60px 굵은 글씨다. 카드 상단의 회사명·거래처·발주일과 SKU·바코드는 표시하지 않는다. 사진→상품명→옵션→주문수량 위치, 주소 확대, PNG 일치를 실제 브라우저 캔버스 기록과 PC/모바일 화면에서 검증했다. 수정 범위 타입 진단 0건이다.

## 상품 사진 붙여넣기와 드래그

- 초안 카드 클릭 후 Ctrl+V, 사진 파일 한 장 드롭을 같은 저장 경로에 연결했다. 드롭 영역을 강조하고 비이미지·여러 이미지·웹 링크는 안내한다. 입력칸의 일반 텍스트 붙여넣기는 유지한다.
- 직접 업로드한 상대경로 사진은 외부 이미지 프록시를 거치지 않고 불러오도록 수정했다.
- 실제 브라우저의 ClipboardEvent/DragEvent와 저장 reducer를 사용해 두 방식의 사진 저장·미리보기, 중복 업로드 차단, 수정 중 수량 보존, 전송 후 사진 잠금을 격리된 API 응답으로 검증했다. 운영 사진·제품DB에는 쓰지 않았다.

## 거래처 답변 4가지 경로 화면 검증

- 거래처 수정 후 서버에 이동은 저장되지만 대상 초안에 상품이 바로 보이지 않는 문제를 실제 화면에서 재현했다. 성공 응답의 대상 초안과 상품을 기존 편집 내용에 병합하도록 연결했다. 추가 자동 조회 없이 반영하며 다른 상품의 미저장 주문수량은 유지한다.
- `verify-vendor-result-browser.cjs`에서 실제 화면의 단종·미납분재발주요청·거래처 수정·입고지연 버튼을 조작했다. 저장 reducer와 실제 재발주 이동 함수를 메모리 저장소에 연결했다. 모든 API를 가로채고 외부 접속은 차단했다.
- 기존 초안으로 이동한 상품의 즉시 표시, 미저장 수량25 유지, 새 거래처 초안 즉시 생성, 재발주에 거래처 주문12 대신 원본 미납2 반영, 새로고침 후 원래 발주서에 지연 상품만 남는 것을 확인했다. 남은 지연 상품까지 다른 거래처로 옮기면 원래 발주서의 미처리 상품은 0개가 된다.
- 단종의 외부 저장 응답은 메모리 대체이며 실제 Google Sheets 기록은 검증하지 않았다. 파일 생성·완료 연결은 위 별도 검증 기록의 범위이며, 이번 화면 테스트로 실제 쿠팡 업로드나 카카오톡 전송까지 검증한 것은 아니다.
- 수정한 두 컴포넌트 타입 진단 0건. 이번 변경의 커밋·push·배포·운영 데이터 변경은 하지 않았다.

## Aside 진행중 19건 이관과 추가 발주서 번호

- 과거 파일에는 마감 쉽먼트 자료와 출고 시 확인한 미입고 사진 자료가 섞여 있다. 마감 상태나 박스번호를 만들어 넣지 않고, 사용자가 확정한 Aside 원본 근거를 별도 필드로 보존했다. 거래처 변경 후에도 근거를 이어가며 공용 미납분 재발주요청 대기·파일 생성·완료 처리로 연결한다.
- 추가 발주서 표시는 `거래처명` → `거래처명-1` → `거래처명-2`다. 숨겨진 전송 이력도 번호를 유지한다. 미전송 초안은 재사용하고, 전송완료만 있으면 새 초안을 만든다. 생성 직후 이전 전송 상품이 새 초안에 섞여 보이던 화면 갱신 문제도 수정했다.
- 검증: 저장한 실제 19행의 격리 화면에서 4개 발주서·19개 결과 카드·지연10/미답변9 확인. 운영 주간 자료 복사본에서 19개 모두 재발주 대기로 이동 성공. 별도 메모리 검증에서 XLSX·파일 증빙 완료·중복 재시도·거래처 변경 근거 보존 통과. 브라우저에서 `-1`·`-2` 생성 직후 새 상품만 표시되고 기존 전송 주문이 보존됨을 확인했다.
- 운영 **데이터 이관은 완료**, 새 화면 및 후속 연결 **코드는 로컬 검증까지만 완료**했다. 커밋·push·배포와 실제 단종·재발주 제출은 하지 않았다.
