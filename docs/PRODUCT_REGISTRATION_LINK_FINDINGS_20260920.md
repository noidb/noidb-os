## 원인과 검증 결과

- 제품DB SKU 공란을 화면이 'SKU 발급 전'으로 잘못 단정했다.
- WIMS 저장자는 {capturedAt, snapshot, capture}를 저장하지만 새 목록은 최상위 rows를 읽었다. 또한 localhost와 운영 사이트, 서로 다른 브라우저의 localStorage는 공유되지 않는다.
- 읽기 전용 대조 API 결과는 승인 연결 후보 1건(wn00272-SI), 재등록 이력 확인 불가 4건이다. WIMS 미수집만의 문제가 아니다.
- _SKU교체이력에는 wn011365RG/GO/SI가 있지만 현재 옵션코드는 wn011365-RG/GO/SI다. mn000008S는 현재 mn000008-SI와도 다르다. 이력 조회가 정확한 이전 모델SKU만 사용해 4건을 찾지 못한다.
- 이전 SKU: mn000008S=39135975, wn011365RG=37880241, wn011365GO=38290788, wn011365SI=40446532, wn00272 이전 SKU=38256597. 이전 바코드와 SKU는 새 등록에 복사하면 안 된다.
- 하트 3옵션 이력 시각은 2026-09-10T06:15:28.749Z, WIMS 등록 시각은 같은 날 15:18:44 KST다. 목걸이 이력은 2026-09-11T00:39:39.719Z, WIMS 등록 시각은 2026-09-14 10:58:38 KST다.
- WIMS 승인 반영 기능은 상품명, SKU, 바코드, 현재상태를 기록한다. 쿠팡 제품주소까지 자동으로 생긴다는 이전 안내는 부정확했다. 실제 상품주소와 옵션 식별자는 별도 출처에서 확인해야 한다.

## 최소 복구안

1. 위 5개 옵션의 구·신 옵션코드와 SKU 연결표를 검토한다. 같은 모델명만으로 묶거나 모든 하이픈을 제거해 자동 연결하지 않는다.
2. 4건은 명시적인 구·신 모델SKU 연결 정보를 재등록 검증에 제공하는 보완이 필요하다. 이전 SKU 차단, 등록시각 비교, 복수후보·바코드 충돌 차단을 유지한다.
3. 5건 모두 읽기 전용 대조를 통과한 뒤 제품DB 백업 → 해당 행의 상품명·신규 SKU·신규 바코드·완료 상태만 반영 → 재조회 검증한다. 이번 조사에서는 시트를 변경하지 않았다.
4. 신규 SKU별 실제 제품주소를 확인해 별도로 연결한다. 대표이미지는 기존 Drive 주소를 유지하고 화면에서 로딩 성공을 검증한다.

## 이번 로컬 수정

상품 연결 대장의 저장 형식 읽기 오류와 오해를 부르는 상태 문구를 수정했다. WIMS 값은 연결 후보로 구분해 표시하며, 실제 DB 값으로 임의 대체하지 않는다. 운영 배포는 하지 않았다.
