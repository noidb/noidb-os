# 2단계 수정 계획 — 쉽먼트 마감과 입고결과

상태: 사용자가 Aside 기록과 수정 진행을 승인했고 로컬 구현·검증을 진행했다. 결과와 미검증 범위는 `PHASE2_LOGISTICS_HANDOFF_20260920.md`에 기록한다. 사용자 화면 검토 전이며 운영 데이터 반영·확장 설치·배포는 실행하지 않았다.

## 목표와 사용자 동작

1단계에서 출고완료한 쉽먼트와 9월 17일 당시 미마감이었던 쉽먼트를 한 목록에서 추적한다. 사용자가 발주번호를 일일이 검색하지 않는다.

권장 수집 동작은 Chrome의 로그인된 쿠팡 쉽먼트 화면에서 `입고결과 일괄 가져오기` 한 번이다. 기존 확장의 읽기 전용 수집·전송 기능을 재사용한다. 성공한 수집 결과만 NOID-B에 저장하고, NOID-B 화면에서는 `새로고침`으로 저장된 결과를 확인한다. 조회 진행/실패/저장 성공을 구분하며 중복 실행을 막는다. NOID-B 화면 진입이나 탭 전환으로 쿠팡을 자동 재조회하지 않는다.

현재 Codex 내장 브라우저에서의 자료 확인 성공과 Chrome 확장의 실제 설치·연결 성공은 별개다. 설치본 버전은 미확인이다. 확장 수정본은 로컬 검증 후 사용자 화면 확인 단계에서 기존 설치본의 갱신 방법을 안내한다. 운영 API는 배포 승인 전에 시험 전송하지 않는다.

## 화면

1단계의 디자인·헤더 여백을 이어받아 `입고결과` 화면을 만든다.

- 상단: 마지막 확인 시각, 수집 성공/실패, 전체 건수, 새로고침.
- `마감 대기`: 입고예정일 → 센터 → 쉽먼트 순. 일부 입고돼도 마감 전에는 미납 확정하지 않는다.
- `입고결과 처리`: 새로 마감된 쉽먼트의 납품/입고/미납수량, 초도 1개 후보.
- `처리 이력`: 이전 처리완료와 이번 처리완료. 기본 작업 목록에 재등장하지 않는다.
- `확인 필요`: 누락·합계 불일치·마감 입고0·기존 자료 연결 불명확 등을 구체적 사유와 함께 표시한다. 실패를 0건이나 완료로 표시하지 않는다.

## 자료에서 확인한 사실

- 기존 확장 `supplier-hub-poc` v0.9.3 소스는 발주번호들을 받아 목록을 수집하고 마감 상세를 읽는다. 전체 대상 자동 구성은 아직 없다.
- 기존 입고 화면은 발주번호 직접입력 중심이며, 미납 계산은 발주 확정수량에서 입고수량을 뺀다. 이를 새 쉽먼트 계산에 그대로 쓰지 않는다.
- 실제 쿠팡 상세 `50129650`: 현재 마감, 발주 2건, 납품16/입고11. 9월17일 기록에는 발송완료11/16이었다. 입고예정일9월4일을 기준으로 제외하면 안 되는 실제 사례다.
- 실제 쿠팡 상세 `50129649`: 현재 발송완료, 납품43/입고33. 미납10으로 확정하지 않고 기다린다.
- 상세 표에는 박스번호, 발주번호, SKU, 바코드, 납품수량, 입고수량이 있다. 박스 rowspan을 처리하고 총합을 대조해야 한다.
- 쿠팡 마감시각은 이번 확인 자료에서 확보하지 못했다. 9월17일 당시 상태가 저장된 파일을 초기 기준으로 쓴다.

## 계산과 저장 기준

- 미납 = 마감된 쉽먼트의 행별 실제 납품수량 - 실제 입고수량. 발주 확정수량으로 대체하지 않는다.
- 식별은 쉽먼트 + 박스 + 발주번호 + SKU. 화면에서 SKU별로 묶더라도 원래 행과 수량 연결을 보존한다.
- 같은 발주의 다른 쉽먼트가 미마감이어도 마감된 쉽먼트만 독립 판정한다. 발주 전체의 업무완료는 모든 관련 쉽먼트와 후속 업무가 끝나야 한다.
- 수량은 가산 이벤트가 아닌 조회 시점의 전체 값이다. 재수집·재전송으로 수량이나 큐가 늘지 않도록 한다. 오래된 자료는 최신 결과를 덮지 않는다.
- 총 납품/입고 합계, 상세행, 참조한 발주번호를 검증한다. 실패·누락·예상하지 못한 상태에서는 미납 확정/완료를 막는다.
- 입고1개는 우선 후보일 뿐이다. 누적 입고와 이전 처리완료·마케팅 제외 기록을 대조한다. 수집한 쉽먼트의 수량만으로 최초 입고라고 확정하지 않는다. 입고횟수/시점 증빙이 부족하면 후보로 남긴다.
- 분류가 완료되면 원래 미처리 목록에서 빠지고 대상 작업 목록에서 이어진다. 서류 생성과 쿠팡 처리완료는 별도 상태다. 모든 후속 업무가 끝나면 이력만 남긴다.

## 구현 순서와 범위

1. 수집 대상 자동 구성과 기존 확장의 일괄 수집/전송: 신규 출고와 이전 미마감 포함, 합배송 상세의 모든 발주 식별, 실패 재시도, 불완전 수집 차단.
2. 쉽먼트 중심의 계산·초기 처리 기준·중복 방지: 기존 미커밋 수정을 보존하며 연결. 초기 자료는 검토 가능한 로컬 데이터로 준비하고 운영 적용은 별도로 확인.
3. 입고결과 화면: 마감대기/처리대상/이력, 날짜별 묶음, 수동 갱신, 초도 후보와 미납 분리.
4. 기존 단종·거래처·재발주·광고/쿠폰 큐의 식별·완료 계약을 필요한 범위만 확인하고 연결한다. 각 관리 화면 자체의 상세 개편은 다음 단계로 분리해 사전 보고한다.

예상 수정 대상은 기존 입고 화면, shipment-receipts 수집·저장 계약, shipment-receipt-shortage 계산, 관련 API, 기존 확장의 shipment-reader/panel/background, 필요한 검사 및 로컬 예시자료다. 공유 저장소의 실제 변경 범위는 구현 전에 확정하고 별도 기능으로 확장하지 않는다.

## 확인할 결과

- 발주20건 이상·합배송·같은 SKU의 다른 발주/박스를 일괄 처리해도 중복되지 않는다.
- 미마감은 계속 대기, 마감 부분입고만 미납, 마감 입고0은 확인 필요.
- 9월17일 마감25건은 새 작업에 안 나오고, 당시 미마감18건은 새 마감 시 나타난다.
- 사진 선처리 행과 기존 거래처 대기가 중복 생성되지 않는다.
- 재수집, 전송 실패, 일부 상세 오류, 페이지 누락, 합계 불일치, 오래된 자료를 검사한다.
- 로컬 예시 화면과 실제 쿠팡 읽기 결과를 구분해 보고한다. 확장부터 운영 저장까지의 검증 전에는 전체 연동 완료라고 하지 않는다.

## 사용량과 반영

조사/구현은 Terra 중간 추론, Astra는 계획·정확성 검토에 집중한다. 단순 일상 수집은 구현된 코드로 처리하는 것을 목표로 하며 실행마다 AI가 모든 페이지를 읽는 방식을 기본으로 하지 않는다.

이번 조사 중 조회된 계정 주간 사용량은14%(남은86%), 별도 시간 단위 한도는 도구에서 제공되지 않았다. 정확한 작업별 사전 크레딧/사용량은 확인할 수 없다.

로컬 테스트와 사용자 화면 확인 후 해당 범위만 커밋한다. push·배포·실제 쿠팡 제출·카카오톡 전송·운영 데이터 일괄 완료는 이 계획 확인만으로 실행하지 않는다.
