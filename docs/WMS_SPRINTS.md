# NOID WMS 스프린트 계획 (초안)

## Sprint 0 — 안전 기반 (현재 완료 범위)

목표: 기존 상품등록 기능을 전혀 건드리지 않고, WMS 개발을 위한 안전한 뼈대만 마련한다.

- [x] 기존 상태에서 `npm run build` 성공 확인
- [x] Git 안전지점 태그(`before-noid-wms`) 생성
- [x] 작업 브랜치(`feature/noid-wms-foundation`) 생성
- [x] `docs/` 기획 문서 4종 작성
- [x] `app/wms/*` 하위 라우트 뼈대(개발 상태 표시용 빈 페이지) 생성
- [x] `lib/wms/types.ts` 공통 타입 초안 작성
- [x] 변경 후 `npm run build` 재확인

Sprint 0에서는 실제 데이터 연동, 상태 관리, API, UI 로직을 구현하지 않는다.
모든 WMS 페이지는 "제목 + 기능 설명 + 개발 상태" 수준의 정적 화면으로만 존재한다.

## Sprint 1 — 발주서 데이터 & 작업센터 기반 (제안)

가장 먼저 구현할 후보:

1. **발주서(PurchaseOrder) 조회 화면**
   - 발주서 번호 기준으로 목록/상세 조회
   - `originalExpectedDate`/`currentExpectedDate`, `originalFulfillmentCenter`/`currentFulfillmentCenter` 표시
2. **작업센터(Work Center) 기초 골격**
   - 발주서 출력 탭을 대체할 화면의 최소 버전(선택 → 목록 표시)
3. **위치 계층(선반 → 박스 → 모델 → SKU) 기준 데이터 조회**
   - 실제 창고 위치 데이터를 읽어와 트리 형태로 표시

이 스프린트는 "읽기 전용 조회" 범위로 한정해 리스크를 최소화하는 것을 권장한다.

## Sprint 2 — 피킹 흐름 (제안)

1. 박스 단위 정렬 피킹 리스트 생성
2. SKU 옵션 이미지 매칭 표시
3. 전량찾음 / 부분찾음 / 현재고 입력 UI 및 상태 저장
4. 부족 수량 → 거래처발주 초안 자동 생성 로직

## Sprint 3 — 거래처발주 & 승인 흐름 (제안)

1. 거래처발주 승인/발송 화면
2. 입고예정일·물류센터 변경 요청 → 승인 → 서플라이어 허브 연동 요청
3. 승인/거부 결과 자동 감지(폴링 또는 웹훅 방식 검토)

## Sprint 4 — 쉽먼트 & 문서 자동화 (제안)

1. 쉽먼트 생성 트리거
2. 거래명세서/라벨 PDF 자동 다운로드
3. 자동 출력 연동(브라우저/프린터 연동 방식 검토)

## Sprint 5 이후 — 신규 발주 자동 감지 (제안, 후순위)

- 브라우저 자동화 기반 신규 발주 감지
- 감지 후 발주서 자동 등록/알림 연동

## 우선순위 판단 기준

- 사용자 승인이 필요한 흐름(거래처발주 발송, 서플라이어 허브 반영)은
  반드시 승인 UI가 먼저 갖춰진 뒤에 자동화한다.
- 외부 시스템(서플라이어 허브, 구글시트) 연동은 읽기 → 쓰기 순으로 리스크를 낮춰가며 확장한다.
- 신규 발주 자동 감지(브라우저 자동화)는 가장 리스크가 높으므로 마지막 단계로 미룬다.
