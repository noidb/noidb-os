# 선반 · BOX 위치 데이터 모델 설계 (Sprint 4)

이 문서는 NOID-B OS WMS의 피킹 화면(Sprint 2~3)이 지금까지 샘플 데이터로만 구현되어 있던
"선반 → BOX → 모델 → SKU" 위치 계층을, 실제로 어떻게 저장·조회할지에 대한 설계안이다.
**아직 구현하지 않았으며, 실제 구글시트 탭도 만들지 않았다.** 이 문서는 다음 스프린트에서
실제로 연동하기 전에 구조를 확정하기 위한 설계 문서다.

## 1. 정정 (2026-08-18): 기존 "창고번호"는 노이드비 내부 보관 위치 정보다

> **이전 버전의 이 문서는 "창고번호"를 쿠팡 로켓배송 측 물류센터/구역 코드(외부 식별자)로
> 추정했다. 이는 틀린 추정이었고, 사용자가 직접 정정했다: "창고번호"는 처음부터
> 노이드비 내부 상품 보관 위치 정보였다.** 아래 내용을 이 기준으로 수정한다.

기존 코드(`app/page.tsx`, `templates/구글시트_상품DB_연동.gs`)에 이미 존재하는
**"창고번호"** 필드는 사용자가 상품 등록 시 수기로 입력하는 자유 텍스트 한 칸이며
(`app/page.tsx`의 입력 placeholder: `예: 711(592) · 미정이면 비워두세요`), `발주서 출력`
시트에도 그대로 실려 나간다(`PO_PICKING_HEADERS`의 `창고번호` 컬럼). 이 값은 **우리 회사
내부에서 실물을 어디에 보관했는지 나타내는 정보**였다 — 다만 지금까지는 "선반 → BOX → 모델
→ SKU"처럼 구조화되어 있지 않고, 자유 텍스트 한 칸에 대략적인 위치를 적어두는 수준이었다.

이번에 설계하는 "Zone/Shelf/BOX" 체계는 그 기존 "창고번호"를 **구조화하고 대체**하는
새 위치 관리 방식이다. 기존 값은 새 BOX 체계로 옮길 때 참고하는 `legacyLocation` 값으로
취급하며, 자동으로 믿고 확정하지 않고 **사람이 실물 위치를 직접 확인한 뒤** 새 BOX ID와
매핑한다 (자세한 절차는 `docs/WAREHOUSE_MIGRATION_PLAN.md` 참고).

| 구분 | 창고번호 (기존) | Zone/Shelf/BOX (신규 설계) |
|---|---|---|
| 소유 주체 | 노이드비 내부 (기존 상품등록 기능이 관리하는 필드) | 노이드비 내부 (WMS가 새로 관리) |
| 저장 위치 | `제품DB`, `발주서 출력` 시트의 기존 컬럼 | 신규 시트 탭(제안) |
| 구조화 수준 | 자유 텍스트 한 칸 (구조화 안 됨) | Zone → Shelf → BOX로 구조화 |
| 수정 대상 여부 | **기존 상품등록 기능 소유 — 시트/컬럼 자체는 수정 금지** | WMS가 새로 관리 |
| 관계 | 새 체계의 `legacyLocation` 참고값으로 활용(마이그레이션 시) | 기존 값을 대체하는 목표 상태 |

**결론: 기존 "창고번호" 컬럼/시트 구조 자체는 절대 수정하지 않는다** (이번 스프린트 규칙:
기존 구글시트 시트명·열·수식 변경 금지). 다만 그 안의 값은 새 BOX 체계로 이전할 때
"참고할 만한 기존 위치 정보"로 취급하며, 완전히 무관한 정보로 보지 않는다.

## 2. 엔티티 구조

```
Shelf(선반)          — 사람이 붙인 라벨 (예: "A-1", "B-2"). 별도 관리 테이블 없이
                       BOX 레코드에 붙는 라벨로 취급한다 (아래 "열린 질문 4" 참고).
  └─ WarehouseBox(BOX) — 실제 보관 박스 1개. 선반 위에 놓인다.
       └─ SKU 위치 레코드 — "이 SKU는 지금 이 BOX 안에 있다"는 매핑 1건.
            (모델은 SKU에서 파생되는 정보이므로 별도 계층이 아니라
             조회 시 SKU→모델 조인으로 얻는다. 단, 피킹 화면에서 빠른 그룹핑을
             위해 모델명을 위치 레코드에 비정규화해서 같이 둘 수 있다 — 열린 질문 참고)
```

### 핵심 규칙(초안)
- **한 시점에 한 SKU는 정확히 하나의 BOX에만 존재한다고 가정한다** (v1 단순화, 아래 열린 질문 1 참고).
- BOX 하나에는 여러 SKU(여러 모델의 여러 옵션)가 섞여 들어갈 수 있다 — 이것이 바로
  Sprint 2~3에서 구현한 "같은 BOX는 한 번만 열도록 묶어서 표시"가 필요한 이유다.
- SKU ID가 위치 레코드의 고유키다 (`skuId` 기준 1행).

## 3. 제안하는 구글시트 탭: `창고위치` (신규 탭, 기존 탭 무변경)

| 컬럼명 | 설명 |
|---|---|
| SKU ID | 제품DB의 SKU ID와 동일한 값 (조인 키) |
| 모델명/품번 | 조회 편의를 위한 비정규화 값 (제품DB에서 파생 가능하지만 조인 없이 빠른 그룹핑을 위해 중복 저장) |
| 선반 | 예: `A-1` |
| BOX | 예: `P-03` |
| 최근수정일시 | 마지막으로 위치가 확정/변경된 시각 |
| 수정자 | (선택) 누가 위치를 지정했는지 |

**이 탭은 기존 `제품DB` / `발주서 출력` / `_SKU마스터` 등 어떤 기존 탭의 헤더·수식·데이터도
건드리지 않는, 완전히 새로 추가되는 탭이다.**

## 4. 조회 시 데이터 결합 방식 (Sprint 1 패턴 재사용)

Sprint 1에서 만든 `lib/wms/purchase-orders.ts`가 `발주서 출력` + `제품DB`를 SKU ID로 조인했던
것과 동일한 패턴을 그대로 확장한다:

```
발주서 출력 (SKU, 발주수량, 입고예정일, 물류센터...)
      +
제품DB (SKU, 상품명, 이미지, 거래처...)
      +
창고위치 (SKU, 선반, BOX)              ← 이번에 새로 추가되는 부분
      ↓
피킹 화면이 쓰는 "선반 → BOX → 모델 → SKU" 뷰
```

세 시트 모두 **SKU ID를 공통 조인 키**로 사용하므로, 기존 `lib/wms/google-sheets.ts`의
읽기 전용 클라이언트를 그대로 재사용해 `창고위치` 탭만 추가로 읽어오면 된다. 새로운 인증/연동
방식이 필요 없다.

## 5. `lib/wms/types.ts`에 반영된 내용

기존 Sprint 0 초안의 `WarehouseBox` / `WarehouseLocation`은 이미 이 설계와 대체로 일치했다.
이번에 다음을 보완했다 (타입 정의만 변경, 로직/화면은 변경하지 않음):
- 이 위치 계층이 기존 "창고번호"(노이드비 내부 위치 정보, 구조화되지 않은 자유 텍스트)를
  구조화·대체하는 관계라는 점을 주석으로 명시
- 위치를 마지막으로 수정한 사람을 남길 수 있도록 `updatedBy?` 선택 필드 추가
- 향후 실제 시트 컬럼과 1:1로 매핑되도록 필드 설명 보강

## 6. 아직 결정되지 않은 질문 (구현 전 확인 필요)

1. **한 SKU가 여러 BOX에 분산 보관되는 경우를 지원해야 하는가?**
   지금은 "1 SKU = 1 BOX"로 단순화했다. 실제로 물량이 많아 한 SKU가 여러 박스에 나뉘어
   보관된다면 구조를 1:N으로 바꿔야 한다.
2. **`창고위치` 시트는 누가, 어떻게 입력하는가?**
   처음에는 창고 담당자가 시트에 직접 수기 입력하는 방식으로 시작할지, 아니면 WMS 화면 안에
   "위치 지정" UI를 먼저 만들지 결정이 필요하다 (이번 설계는 시트 수기 입력을 v1으로 가정).
3. **BOX 자체의 메타데이터(용량, 크기, 현재 사용 여부)가 필요한가?**
   지금은 BOX를 단순 라벨로만 다룬다.
4. **"선반"을 별도 관리 대상으로 둘 것인가, 단순 라벨로 둘 것인가?**
   지금은 BOX에 붙는 라벨 문자열로만 취급했다(선반 테이블 없음). 만약 선반별 위치(층, 구역)
   정보가 필요하면 별도 `Shelf` 엔티티가 필요하다.
5. ~~기존 "창고번호"와 새 Zone/Shelf/BOX 사이의 관계~~ → **해결됨(2026-08-18)**: 창고번호는
   노이드비 내부 위치 정보이며, 새 BOX 체계로 옮길 때 `legacyLocation` 참고값으로 쓴다
   (`docs/WAREHOUSE_MIGRATION_PLAN.md` 참고).
